# Marketing CRM code-review audit

Audited on 2026-09-19 against the implementation plan. This document describes commit `077bac278d4f8be4bcbfd905202e51f8ab1bac40` plus review-preparation tests added afterward. Migration 031 has not been applied to production or a review database.

## Findings by requested control

1. **Contactability — incomplete (data/compliance risk).** `marketing_contacts.recipient_category` supports `individual`, `legal_entity`, and `unknown`. There is no endpoint-level permitted-channel, consent/legal-basis, evidence-date, review-date, or evidence record. A source URL is provenance only and is not treated as permission, but the system cannot yet prove eligibility.
2. **Phone normalization — implemented at the import boundary.** `+370`, bare `370`, domestic `0`, legacy `8`, and international `+` numbers with 8–15 digits normalize to E.164-like values. Foreign numbers are not forced to `+370`. Raw and normalized values are stored. Local validation is structural, not full country/type validation.
3. **Email normalization — implemented.** Whitespace is trimmed, comparison candidates are case-normalized, and raw input is retained. Dots and plus-tags are preserved. No provider-specific rewriting exists.
4. **Duplicate/conflict rules — substantially implemented.** Exact identity matches resolve existing contacts; phone A plus email B is a conflict. Database uniqueness and an advisory transaction lock protect concurrent imports. Imports do not update lifecycle status, suppressions, or enrollments; blank fields and marked manual corrections are preserved. Source natural keys prevent identical source duplication. A repeat import creates another import-batch record but not another contact.
5. **Import error report — incomplete.** Preview returns all five outcomes. `marketing_imports.error_report` exists, but commit code does not populate it and there is no download route/button.
6. **Contacted transition — foundation-safe but unfinished.** Draft creation/approval does not set `contacted`. There is no transport/manual-Telegram confirmation operation yet, so the required positive transition is pending.
7. **Limits and sequences — configuration only.** Defaults are stored: 5/10 new contacts, 20 proactive messages, Telegram→email→SMS, four days, weekdays, 09:00–18:00 Europe/Vilnius, three attempts, approval required, automatic acquisition sending absent. `dispatchEligibility` accepts already-computed booleans, but no worker/server transaction calculates or enforces counters, channel order, attempts, calendar, or window. Dispatch must remain disabled until server-side enforcement exists.
8. **Approval revision safety — partial.** Approval atomically checks and records the exact revision and stores rendered body/recipient/channel/account on the draft. Editing body, recipient, or channel increments revision and clears approval. Template edits cannot rewrite draft content. Sending-account edits are not exposed by the route and no database trigger invalidates approval after arbitrary service-role mutation. An edited approved draft can leave an old queue row present; a future worker must reject/cancel it through revision checks.
9. **Replies — implemented at database insert boundary.** Any inbound message trigger sets unread/needs-reply, pauses active enrollments, updates eligible lifecycle states, and cancels queued/leased work without AI. Conversations allow null contacts and `needs_matching`, `needs_reply`, and `resolved`. Unmatched inbound ingestion/API is not implemented yet.
10. **Opt-out — pending.** Suppression storage exists, but deterministic Lithuanian/English opt-out parsing and transactional suppression/cancellation logic do not.
11. **Registration — partial.** A profile insert/update trigger normalizes identity candidates. One distinct matching contact is linked/registered and outreach is cancelled; multiple contacts are paused and returned as conflicts. The import-time existing-profile phone lookup compares stored phone text directly to the normalized value, so noncanonical historical profile formatting may be missed. There is no scheduled reconciliation job. Review items are represented by events/pause reasons, not a dedicated review queue.
12. **Send queue — partial future-worker support.** It has draft/contact, due time, state, lease owner/expiry, attempt count, idempotency key, error, transport job, completion and timestamps. It lacks explicit `last_attempt_at`, structured outcome/provider response, `cancelled_at`, and cancellation reason fields. `last_error` is currently overloaded for cancellation reasons.
13. **Messages — implemented model.** It supports matched/unmatched contact, conversation, per-message channel/account, direction, body, full requested state enum, external message/thread/event IDs, and created/sent/received/delivered times.
14. **Cross-channel timeline — implemented model.** Conversation has no channel column; every message owns its channel.
15. **API security — partial.** All four routes authorize before service-role access. Only the import route accepts the constant-time checked `MARKETING_IMPORT_API_KEY`. Service-role secrets remain server-only. Contact reads paginate. Input checks are ad hoc rather than schema-based; import and database error messages can expose internal details. Mutation idempotency, OpenAPI, and scoped agent roles beyond import do not exist.
16. **RLS/database security — structurally implemented, not database-verified.** All 17 marketing tables enable RLS, revoke `public`/`anon`/`authenticated`, and grant service-role access. Security-definer functions revoke browser-role execution. No public route intentionally queries marketing tables. This has not been exercised against a migrated Supabase review database.
17. **Audit/pauses/retention — incomplete.** Events are written for some important actions, but the table is not database-enforced append-only against service-role updates/deletes and coverage is incomplete. Global pause exists only as a setting (default `true`); per-channel pause can be represented by channel-account status but is not enforced. Errors are individual fields, not an actionable aggregate list. No agreed retention policy/model exists. Identity-scoped suppressions survive contact deletion; contact-only suppressions can fail preservation because `ON DELETE SET NULL` conflicts with the row check when no normalized identity is present.

## Test evidence and limits

Unit coverage includes all requested phone formats, email normalization invariants, duplicate phone/email, cross-contact conflict, repeat import, blank/manual-field protection, invalid rows, revision checks, registered/suppressed/reply eligibility, ambiguous-registration SQL path, RLS/revokes, and unauthorised route rejection. Source-level SQL assertions are not a substitute for applying migration 031 to a disposable review database. Suppression/source survival and database-trigger behavior are represented by schema/source checks rather than database integration tests; these remain unverified until a non-production database is authorized.

## Review blockers before live sending

- Model and enforce endpoint-specific contactability evidence.
- Add deterministic opt-out processing.
- Add transactional server-side dispatch enforcement and complete queue operational fields.
- Close approval invalidation for sending-account changes and stale queue rows.
- Harden validation/error responses, then add mutation idempotency and scoped roles.
- Fix/review suppression deletion retention and append-only audit guarantees.
- Validate migration 031 and database behavior on a non-production Supabase branch/local stack.
